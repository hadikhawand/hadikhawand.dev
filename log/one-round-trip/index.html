One round trip instead of five: psycopg pipeline mode in front of RLS

Yalla's map calls spent almost all their time waiting for the network, not the database. Waiting once instead of five times took them from around 600 ms to around 250.

Hadi Khawand 21 Nov 2026 7 min read

Yalla is the app my teammate and I are building as our senior project: a map of things to do in Lebanon and a way for friends to plan around it. The database lives on Supabase in Frankfurt. The backend runs in Python with FastAPI and talks to Postgres through psycopg.

While working on map speed, I measured where a map call actually spent its time. The query itself took a few milliseconds. The call took 500 to 900.

Where the time went

Every read the backend makes for a user has to run under that user's Row Level Security rules. So a read is not one statement. It is a small transaction, roughly like this:

begin;
set local role authenticated;               -- act as a signed-in user
select set_config('request.jwt.claims', ...);  -- tell Postgres who it is
select ... from activity where ...;         -- the actual query
commit;

The old code sent each statement, then waited for the answer before sending the next one. Each wait is one round trip: a message to Frankfurt and the reply back to Beirut, about 100 to 200 ms. A map call made 4 to 6 of those trips. The database was fast. We were just waiting on the network most of the time.

Send everything, wait once

Postgres has a pipeline mode, and psycopg supports it. In a pipeline the client sends several statements without waiting, and reads all the answers at the end. Same statements, same order, same transaction on the database side. Only our waiting changes.

The core of the new db.as_user looks like this. I wrote the pipeline design. My teammate later moved it into a shared helper when another reader was added:

with pool.connection() as conn:
    conn.autocommit = True  # we send BEGIN / COMMIT ourselves: psycopg's own would wait
    try:
        with conn.pipeline():
            conn.execute(begin)
            for statement, params in setup:
                conn.execute(statement, params)
            yield conn
            conn.execute("commit")
    except BaseException:
        if not conn.closed and conn.info.transaction_status != IDLE:
            conn.execute("rollback")
        raise

The endpoints run their query inside the block and read the rows after it, so the whole read becomes one trip.

The obvious versions didn't work

Before choosing, I prototyped five designs against the real endpoints and counted the trips on the wire with a small relay script. Two results changed the design.

psycopg's own pipeline transaction saved nothing. When psycopg manages the transaction inside a pipeline, it still stops to check the state before deciding whether to commit. The trip count stayed at 5 or 6. That is why the code above turns autocommit on and sends begin and commit itself.

Pipelining the writes broke accepting a friend request. That endpoint checks .rowcount to make sure its update really changed one row. Inside a pipeline, .rowcount is -1 until the answers arrive, so the check stops working. Writes are rarer than reads, so only as_user, the reading path, uses the pipeline. as_admin stayed exactly as it was.

The part that could have leaked data

One variant skipped the explicit begin and relied on the implicit transaction. That one I rejected for security, not speed. If anything in the block forced a sync partway through, the implicit transaction would end there, and the next statement would run as the connection's real user, postgres, with Row Level Security not applying. A faster query that can skip the access rules without any error is not an option. With an explicit begin, the role and the claims are the first things inside the transaction, and everything after them runs under them.

A second, smaller fix

psycopg prepares a query from its sixth run, and Postgres can switch a prepared query to a generic plan that ignores the actual values. For the map pins that generic plan could not use the category index. With one category on the live database, the value-aware plan took 1.9 ms and the generic one 18.9 ms. Setting prepare_threshold=None keeps the value-aware plans. psycopg is pinned to version 3.3.6, because the design relies on two behaviours I checked on that version.

Before and after, on live

Measured in one sitting on the live backend, 21 runs per case, alternating old and new code so that the network's mood affected both the same way:

  • /health: 4 trips to 1, median 608 ms to 134 ms (p95 949 to 207)
  • Map pins for the Chouf: 4 trips to 1, median 518 ms to 222 ms (p95 675 to 298)
  • Filter for Mount Lebanon: 5 trips to 1, median 708 ms to 321 ms (p95 1120 to 369)

Our target was a map query under 500 ms at the 95th percentile. Before the change, 0 of 15 measured map calls met it. After, 12 of 15 did.

Testing it by breaking it

I broke the new code on purpose five times, each time writing down first which tests should fail. My predictions were wrong in some detail four times out of five, mostly about how many tests would go red. One break also showed that a claim in my own plan was wrong. A sixth case came from my teammate's review, where a lost connection hid the real error. Writing the prediction first is what made those gaps visible. Without it, a red test just looks like a red test.

What it didn't fix

Three of the 15 map calls still miss the 500 ms target at the 95th percentile, including one far region at about a second. Those are dominated by the network and by the size of the query, not by our waiting. Writes still take 3 to 5 trips. Waiting once also doesn't make that one trip any shorter: it still goes to another country and back.
