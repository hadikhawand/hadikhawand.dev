Building a food delivery backend in Node.js without Express

DeliveryApp has three kinds of users, about 30 routes and no web framework. These are the parts Express usually hands you, written by hand.

Hadi Khawand 21 Nov 2026 8 min read

DeliveryApp is a food delivery web app with three roles. Customers browse restaurants, build a cart and place or cancel orders. Restaurant managers edit their menu, see incoming orders and assign a courier. Couriers see the deliveries assigned to them and update the status as they go.

An order moves through four states:

Submitted  ->  Preparing  ->  On the way  ->  Delivered
(customer)     (manager       (courier        (courier
                assigns        picks up)       delivers)
                courier)

The server is plain Node.js with MySQL. There is no Express, no Fastify, no templating engine. The whole dependency list is mysql2, bcrypt for password hashing, uuid for IDs, dotenv for config and nodemon for development. Everything else, from routing to cookies to rendering HTML, lives in the project's own files.

One function handles every request

Node's http module gives you a single callback for every request that reaches the server. A login, a page load and a request for a CSS file all land in the same place:

// index.mjs
const server = http.createServer(appRouter);
server.listen(PORT);

So the first thing to build is something that looks at the method and path and decides which code should run.

A router in about 30 lines

The router is a class that keeps a private list of routes. Each route is a method, a path and a handler function:

export class Router {
  #routes = [];

  add(method, path, handler) {
    this.#routes.push({ method: method.toUpperCase(), path, handler });
  }

  dispatch = async (req, res) => {
    const { pathname } = new URL(req.url, `http://${req.headers.host}`);
    const match = this.#routes.find(
      (r) => r.method === req.method && r.path === pathname
    );
    const handler = match ? match.handler : this.#notFound;

    try {
      await handler(req, res);
    } catch (error) {
      errorController(HTTP_STATUS.SERVER_ERROR, req, res);
    }
  };
}

Two decisions are baked in here. First, matching is exact: a route only fires when both the method and the path are equal, so there are no path parameters like /orders/:id. IDs travel in the form body instead. Second, every handler runs inside a try/catch. The controllers catch their own errors too, but if something slips past them, the user still gets the 500 page and the server keeps running.

Reading a form body

The request body does not arrive as an object. It arrives as a stream of chunks, and for an HTML form it looks like userEmail=karim%40example.com&password=secret123. The parser collects the chunks and decodes them with URLSearchParams:

export const parseBody = (req) =>
  new Promise((resolve) => {
    let raw = "";
    req.on("data", (chunk) => (raw += chunk));
    req.on("end", () =>
      resolve(Object.fromEntries(new URLSearchParams(raw)))
    );
  });

That is the entire body parser. It is short because the app only accepts URL-encoded forms. It also has no size limit yet, which I come back to at the end.

Sessions stored in the database

After a successful login the server creates a random token, saves it in a Session table next to the user's ID and role, and sends it back as a cookie:

const token = randomBytes(32).toString("hex"); // 64 hex characters

await db.query(
  "INSERT INTO Session (token, userId, role, userEmail, restaurantName) VALUES (?, ?, ?, ?, ?)",
  [token, user.userId, role, user.email ?? null, user.restaurantName ?? null]
);

res.setHeader(
  "Set-Cookie",
  `token=${token}; HttpOnly; Path=/; SameSite=Strict; Max-Age=3600`
);

The cookie flags each do one job. HttpOnly keeps JavaScript on the page from reading the token. SameSite=Strict stops the browser from sending it on requests that start on other sites. Max-Age=3600 makes it expire after an hour.

The token itself means nothing to the client. On every protected request the server reads the cookie and looks the token up in the table. Logging out deletes the row, so that token stops working immediately. A signed JWT works differently: it stays valid until it expires unless you also keep a list of revoked tokens. The cost of the database approach is one extra query per request.

Checking who is allowed to do what

Logging in only proves who you are. Each action still has to check whether you are allowed to do it. Cancelling an order is a good example, because three separate things have to be true:

// POST /order/cancel
const { userId } = await verifyToken(req);       // 1. someone is logged in
const { orderId } = await parseBody(req);
const order = await repository.findById(orderId);
if (!order) return errorController(HTTP_STATUS.NOT_FOUND, req, res);

if (order.customerId !== userId)                  // 2. it is their order
  return errorController(HTTP_STATUS.UNAUTHORIZED, req, res);

if (order.status === OrderStatus.ONTHEWAY ||      // 3. it has not left yet
    order.status === OrderStatus.DELIVERED)
  return errorController(HTTP_STATUS.BAD_REQUEST, req, res);

The second check is the one that is easy to forget. Without it, any logged-in customer could cancel anyone's order just by changing the hidden orderId field in the form.

Right now each controller writes these checks inline. To stop repeating them, I wrote a small Guard class where each step either passes or throws:

const guard = await new Guard().authenticate(req); // is anyone logged in?
guard.authorize("Customer");                        // is it the right role?
guard.requireOwnership(order.customerId);           // is it theirs?

The controllers don't use it yet. Moving them over is on the list below.

Where the rest of the code lives

  • Controllers/ read the request, call the models and repositories, and send the response.
  • Filters/ has one DTO per form, such as CreateOrderDTO and AssignCourierDTO, so each input is shaped and checked in one place.
  • Models/ hold the business rules for users, orders, restaurants and deliveries.
  • Database/ has a single shared MySQL connection pool and one repository per table. Every query uses ? placeholders, so user input never gets pasted into SQL.
  • Views/ are plain HTML files. A small renderHTML helper reads the file and swaps every {{key}} for a value.

The tables are created with CREATE TABLE IF NOT EXISTS when the server starts, so a fresh setup only needs an empty database and a .env file.

What is still missing

Writing it by hand also makes the gaps easy to see. These are next:

  • Escape values in templates. renderHTML inserts values as they are. If a restaurant name contained <script>, it would run in every customer's browser. Each value needs <, >, & and quotes escaped before it goes into the page.
  • A body size limit. The parser keeps appending chunks until the request ends, so a client could send a huge body. It should count bytes and reject the request past a few kilobytes.
  • Move the controllers onto the Guard. One chain instead of the same three checks copied into every handler.
  • A logger. Errors currently go to console.log. A small Logger class with levels and timestamps, writing to a file as well as the console, would make problems traceable after the fact.

Express's body parser and a template engine like EJS would have covered the first two for me. Building without them meant I had to notice they were missing.
